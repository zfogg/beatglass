# Playback visualization handoff (provisional)

`PlaybackVisualization` accepts PCM emitted by the same `QMediaPlayer` that plays the Library source. Build with `BEATGLASS_BUILD_PLAYBACK_VISUALIZATION=ON` and Qt Multimedia 6.8 or newer. Qt supports `QAudioBufferOutput` only on its FFmpeg backend; lack of PCM or any terminal tap status must result in an unavailable display, not synthetic data. Qt emits decoded buffers before or near output submission, so the visualization is not a measured speaker-time clock.

The UI/control owner allocates a fresh nonzero process epoch and a new tap for each source and seek generation. Attach `output()` to that generation's player. Before source change, seek, stop, output failure or teardown, synchronously call `retire()`, clear the displayed frame and reject all queued or cached old-generation updates. A fresh tap on an existing decoder does not identify old buffers that the backend emits after a seek; use a fresh player/tap generation and do not admit seek data until the backend's flush and target behavior are verified. Detach and quiesce the player on its owning thread before destroying the tap. A returned frame is owned, but it is not self-revoking: check `isCurrent(frame.value.epoch, frame.revision)` immediately before display and clear it when false. Every published frame gets a strictly increasing revision; the maximum unsigned revision is reserved for terminal invalidation. The tap fails closed before revision wrap, never resets or becomes active again. The UI must also serialize its own final acceptance, clearing and painting so a delayed older delivery cannot replace a newer one. `isCurrent` is only a momentary atomic check: invalidation can race an in-flight paint and cannot revoke pixels already displayed. A control/render-side gate must trigger an asynchronous clear at the next scheduled UI update, including under Reduce motion. The timer interval is a target, not a hard wall-clock bound when the UI or renderer is delayed. Native renderer integration must verify that it never accepts an older delivery after a newer one. The control/UI owner must additionally gate source/session generation across tap replacement.

The direct PCM handler copies only bounded data into preallocated storage; one worker converts samples and computes windows. It accepts up to 4,096 frames, eight channels and 384 kHz per buffer, supports Qt UInt8, Int16, Int32 and Float PCM, averages channels, rejects nonfinite values, and clips finite averages to [-1,1] for display. Missing, over-seven-day or discontinuous timestamps, format changes, oversized buffers, concurrent callbacks or queue overflow make the generation terminal and clear its eligibility for display. Timestamp continuity allows at most two microseconds of rounding; this is a conservative gate, not proof of media identity or exact audible position. Frame positions count accepted frames within the generation and are not track-relative. The latest owned 1,024-frame window is retained; slow polling can drop intermediate windows. No PCM, visualization, or cache identity is written to the source file.

Issue #76 still requires the UI owner to provide selectable scrolling waveform and FFT views, reduced-motion behavior, source-attributed Library browsing/selection/search/sort, actual playback and seek, queue progress/cancel/retry, missing/changed/corrupt-source feedback and recovery. The adapter does not implement those UI states or a queue, and a tap alone does not establish seek flush semantics. Test the real FFmpeg backend and actual output route, generation replacement, repeated seek, timestamp gaps, format changes, overflow, end/stop and shutdown. Native desktop/audio/overlay qualification on Linux, Windows and macOS remains required.

The UI must check generation validity on every paint and poll terminal status on a bounded control timer even when Reduce motion disables animation; disabling motion must not disable stale-frame clearing. Selection and playback source are distinct: bind the tap to the player source that produces PCM, not merely the highlighted Library row. Queue retry/cancel and source recovery remain owned by the Library coordinator and must not infer a source identity from visualization frames.
