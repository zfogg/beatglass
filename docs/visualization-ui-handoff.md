# Visualization and theme UI handoff

## Current behavior

The Library page already selects a local audio file, displays decoded metadata, and uses Qt Multimedia for playback, seeking, output selection, and playback errors. It does not expose playback PCM, a scrolling waveform, FFT data, a visualization mode, or theme cards. The DJ page uses the selected/default Windows output bridge for tempo; its overlay displays status and BPM. It has no waveform or spectrum model. DSP draft #79 supplies a separate worker-owned live composite consumer and is not yet connected to this UI. Its rolling key and local chord are provisional and its generation clears must be carried through the presentation boundary.

The macOS overlay controller already enumerates current display names and can move to a session-local display index. The Windows overlay currently recovers an off-screen window but does not expose a selectable display list. Qt screen order and names are not stable persistent identifiers; a display selector must track screen addition, removal and geometry changes, and initialize from the screen containing the relevant window rather than an assumed index. The shared overlay has a click-through action and a provisional tray/menu recovery contract. Controls remain discoverable until native recovery reachability is verified.

## Required handoffs

- **Real audio data:** the DSP/capture owners should propose a bounded, worker-produced visualization stream for actual monitored output and a separate stream synchronized to the Library playback pipeline. The UI must not synthesize waveform or FFT values. The capture callback continues to copy only into preallocated bounded storage; channel reduction, waveform aggregation and FFT belong on a worker. Playback visualization must correspond to the selected playback source and position rather than a separately decoded stream with untracked timing.
- **Timing and invalidation:** each owned display update needs the source/session generation, sample or frame position, sample rate and a bounded payload. Seek, pause, source change, stop, restart, capture loss, discontinuity, overflow and teardown must clear or re-anchor old evidence as appropriate. The GUI rejects late generations and uses a bounded latest-value handoff; no worker may call QML or retain GUI objects.
- **Presentation contract:** provide selectable waveform and spectrum modes for the Library player and DJ overlay. Empty, unsupported, stopped, buffering and failed states must be explicit; the UI must not imply that unavailable data is silence. Reuse the DSP owner's real producer rather than adding a second live capture. Any live key/chord presentation must remain labeled rolling/local and provisional, with unknown strength left unknown.
- **Theme and motion:** each clickable, keyboard-accessible theme card previews its own palette independently of the currently selected theme and exposes selection accessibly. Persist a user-selected Reduce motion preference; in reduced-motion mode use a stable, legible visualization with less frequent in-place updates rather than relying on continuous scrolling. The click-through and Reduce motion controls must expose their checked state, focus and accessible names.
- **Displays and recovery:** provide a shared, GUI-thread screen model that reports current real displays, refreshes on changes, and resolves the default from the screen containing the window. Revalidate selection before moving an overlay. Do not hide the only discoverable controls unless a platform has established a reliable tray/menu recovery route; loss of the route must unlock or hide the overlay and restore controls. Dock/menu-bar, Explorer restart and X11/Wayland compositor behavior require native qualification.
- **Settings and errors:** place output-device selection and audio-permission guidance in Settings; do not introduce a separate recovery screen. Platform owners must validate macOS permission wording against the actual capture API and OS version before presenting it. When a user interacts with an unavailable file, show a Library alert tied to that file. When analysis stops, surface both an OS notification and an in-app toast; if OS notifications are unavailable or denied, keep an accessible in-app notification and recovery action. Do not report success for a notification that was not delivered.

The macOS owner verified this proposed copy: “System audio access: Beatglass needs permission to monitor audio playing through the selected output. When macOS asks, choose Allow. You can review access in System Settings → Privacy & Security → Screen & System Audio Recording. Settings names may vary by macOS version.” The prototype requires macOS 14.2 or newer and is not connected to the desktop. The app bundle needs `NSAudioCaptureUsageDescription`. A Settings action must not claim to start capture, infer permission from silence or startup, or present denial and recovery as qualified before native testing.

The integration owner coordinates the shared DTO, ownership and build changes with the DSP, Library and platform owners before wiring QML. Tests should cover actual data provenance, generation invalidation, selection/seek races, bounded delivery, mode/theme accessibility, each card's independent palette, reduced motion, display removal and fallback recovery. Synthetic inputs are appropriate only in tests. Local offscreen tests do not replace native playback, audio capture, overlay, accessibility and multi-display checks. Hosted CI and Pages deployment are currently paused by user request.
