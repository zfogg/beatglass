# Essentia tonal dependency spike

This is research, not a supported Beatglass dependency or product estimator. Source under test: [Essentia](https://github.com/MTG/essentia) commit `23ae7baddecfc3227ba23ad69fa11f73ac5293a4`; lightweight KISS FFT build, excluding `Spline,CubicSpline`. No trained models, Essentia decoder, resampler, metadata reader, or model weights are used. The fixture synthesizes simple equal-tempered triads and invokes real Essentia Windowing, Spectrum, SpectralPeaks, HPCP and Key (`tonictriad`, polyphony disabled). It is not a real-music accuracy evaluation.

## Proposed architecture and integration decisions

- Prefer an in-process worker-owned adapter using the pinned Essentia C++ library and existing libsndfile input, with a bounded sample/frame buffer. Keep initialization and shutdown controlled at process scope; instances and all allocations/DSP belong to the worker, never the capture callback. Verify Essentia global initialization and factory use with concurrent workers before enabling concurrency.
- Use Essentia HPCP and Key for key candidates and Essentia's tonic-triad Key profile for an explicitly limited major/minor chord baseline; report raw strengths as uncalibrated, not probabilities. Gate silence and insufficient evidence to unknown. Tuning, alternatives, segment boundaries, discontinuities, sample rates and stability require explicit tests and contracts before publication. A triad is a local chord estimate, not proof of the track's key.
- Upstream `ChordsDetection` computes a centered temporal window and its streaming implementation collects all input before emitting. It cannot be presented as immediate causal output. A live adapter must use only trailing observed HPCP or timestamp a centered result with a declared delay; offline and live configuration identities must differ. The merged shared snapshot contract uses an exclusive observed boundary, beat positions before that boundary and nonempty half-open chord segments; honor it before emitting shared snapshots or storing segments.
- Keep decoder ownership in the existing file source; no Essentia loader is needed for this proposed pipeline. The library worker must still coordinate file lifetime, content identity, cancellation and stale-file checks with the library owner. No tags are written.
- Select a verified build per supported toolchain before enabling this in production. The [upstream Windows instructions](https://github.com/MTG/essentia/blob/23ae7baddecfc3227ba23ad69fa11f73ac5293a4/doc/sphinxdoc/installing.rst) describe MinGW cross-compilation and say those C++ binaries are incompatible with Visual Studio, while a Visual Studio project must be set up separately. Beatglass's Windows build uses MSVC. A reproducible MSVC build or a consciously selected compatible toolchain is a blocker; WSL is not native Windows qualification.

## Licensing decision proposal

Upstream source at the selected commit states AGPL-3.0-or-later; [upstream licensing](https://essentia.upf.edu/licensing_information.html) describes AGPL and commercial licensing choices, separately licensed models, and dependency-specific obligations. The KISS FFT and Eigen choices remove some optional dependencies but do not remove Essentia's own terms. aubio is GPL-3.0-or-later, while this repository's source is MIT. Propose an AGPL-3.0-or-later combined distribution path, preserving Beatglass's own MIT grant, subject to a complete compatibility, source, notices and relinking review for the exact binaries and dependencies. A commercial licensing route is an alternative requiring investigation with the rights holder. This is not legal clearance and does not authorize release. No models are needed for this baseline.

## Reproduction

`docker build -f tests/spikes/essentia/Dockerfile -t beatglass-essentia-spike .` builds the pinned source and runs the synthetic test. The base image digest, source revision and direct Eigen package version are fixed; other Ubuntu packages and Git availability are not snapshot-pinned, so this is a repeatable development experiment, not a hermetic release recipe. Native platform and actual audio qualification remain separate.

## Contract proposal for integration review

Keep per-worker incremental analysis independent of GUI and storage. A beat event carries source epoch and frame position, and must precede the exclusive observed boundary; specify aubio's algorithmic delay and origin mapping rather than presenting callback arrival time as beat time. Tonal updates carry their evidence interval, estimated delay, unknown state, uncalibrated strengths, algorithm/version and configuration identity. Chord segments are nonempty half-open frame intervals; live revisions need an explicit policy for provisional boundaries and invalidation on reset, gap, format change and silence. The exclusive observed boundary and nonempty half-open chord intervals are merged shared guarantees; the evidence, delay, provisional revision and invalidation details remain proposals. Key and chords must not silently fall back to a different estimator if Essentia is unavailable.

## Decoder and cache ownership review (PR #30)

The current `FileReader` opens its own decoder from a path and hides the underlying file; `replay_file` creates and destroys it internally. Consequently the proposed verifier cannot yet prove it is inspecting the same open source that supplied decoded PCM. Reopening the path, even if a hash and attributes match initially, is not a same-handle guarantee. The decoder/library integration needs an owned open-source abstraction that captures native file identity and pre-analysis attributes before decoding, exposes a nonconcurrent way to hash/revalidate the same open file, and keeps that evidence and handle alive through the synchronous database-worker publish call. The decoder must read that open source rather than independently reopening the path. Define handle ownership and failure/cancellation rules for each platform, and transfer or serialize exclusive use when work crosses from analysis to database thread; the current `FileReader` is not thread-safe. Validate what happens if the path is replaced, renamed, truncated or mutated while open, and document platform-specific races between verification and commit. It is unsafe to infer that retaining a path or a completed `TempoResult` retains this evidence. No decoder contract change is implemented by this spike.

The exploratory full algorithm build compiles bundled NNLS and other third-party code even though the smoke path does not call those algorithms. Audit actual object contents, notices and licenses before distributing a static library; merely choosing KISS and excluding Spline does not establish a minimal or cleared artifact. A smaller selected-algorithm build must separately validate transitive registrations and dependencies.

## Observed builds and smoke test

On 2026-11-07, Ubuntu 24.04.5 x86-64 in Docker, GCC 13.3.0, Python 3.12 and Eigen 3.4.0-4build0.1 configured commit `23ae7baddecfc3227ba23ad69fa11f73ac5293a4` with `python3 waf configure --lightweight= --fft=KISS --build-static --ignore-algos=Spline,CubicSpline`, then `python3 waf -j4` completed with upstream warnings. The first standalone compile missed the source and Eigen include paths and failed; after adding `-I src` and `$(pkg-config --cflags eigen3)`, compiling and linking `tests/spikes/essentia/tonal_smoke.cpp` against `build/src/libessentia.a` with `-pthread -latomic` produced `C triad: C major` and `A minor triad: A minor`, exit 0. The container used a copied checkout and did not have Git installed, so the library's embedded Git version could not be validated; the fresh Dockerfile installs Git and checks out the same explicit commit. The container is not native Linux desktop qualification.

On Intel macOS (`Darwin 25.6.0`, x86-64) over SSH, the same checkout, configure flags and `python3 waf -j4` built the static library with upstream Clang warnings. The same smoke source compiled and linked with Clang and `pkg-config --cflags eigen3`, and returned `C triad: C major` and `A minor triad: A minor` (exit 0), with upstream template and linker search-path warnings. SSH does not qualify GUI, device audio, overlay, packaging, Apple Silicon or a release binary. Windows/MSVC and real-music evaluation remain unrun.

The complete clean recipe was then run from this worktree with `docker build -f tests/spikes/essentia/Dockerfile -t beatglass-essentia-spike:recipe .`: it completed successfully, including compiling and running the two-triad smoke test. Source commit and direct Eigen package were pinned as above; transitive Ubuntu packages and remote availability were not.

## Windows x64 MinGW experiment (2026-11-07)

An isolated Ubuntu 24.04 container with `g++-mingw-w64-x86-64-posix` 13.2.0 cross-compiled Essentia `23ae7baddecfc3227ba23ad69fa11f73ac5293a4` as a static Windows x64 library with KISS FFT. Upstream's cross-build script hardcodes i686; the experiment changed that compiler prefix to x86_64 in the container copy only. The build used `python3 waf configure --cross-compile-mingw32 --lightweight= --fft=KISS --build-static --include-algos=Windowing,Spectrum,SpectralPeaks,HPCP,Key,FFT,Magnitude,PeakDetection --pkg-config-path=/usr/share/pkgconfig` and `python3 waf -j2`. The first attempt omitted FFT, Magnitude and PeakDetection and its executable failed at runtime because FFT was not registered; adding those dependencies produced a successful build.

The resulting archive, generated `src/version.h` and Eigen headers were copied out of the container. On Windows x64, Scoop GCC 15.2.0 linked `tests/spikes/essentia/tonal_smoke.cpp` with that archive using `-std=c++17`, includes for Eigen and Essentia sources, and `-static-libgcc -static-libstdc++`. The executable returned exit 0 and printed `C triad: C major` and `A minor triad: A minor`. This links a GCC 13 cross-built archive with GCC 15 on the host; compatibility is not established beyond this smoke run. This does not build Beatglass, aubio or libsndfile with MinGW, is not an MSVC-compatible C++ library, and does not qualify actual Windows audio, UI, packaging, licensing or real-music accuracy. The narrow algorithm list requires further dependency and registration audit. A pinned, fully reproducible toolchain and native combined test remain outstanding.
