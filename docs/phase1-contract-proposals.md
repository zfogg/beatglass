# Proposed initial Phase 1 contract decisions

**Review status:** the snapshot timeline boundary, typed cache outcomes, and source/clock contracts were merged in PRs #21, #30, and #28 respectively. Their interfaces do not implement the corresponding platform, database, or delivery paths; remaining proposals require integration-owner acceptance. The owner owns `include/beatglass/`, result and database schemas, root CMake, dependency definitions and CI. Agents may implement behind private adapters in isolated worktrees, but must propose shared API/schema changes before another workstream depends on them. See [foundation ownership](foundation-handoff.md). The real CLI currently produces tempo only; no proposal below implies that capture, storage, key, chords or the UI pipeline already work.

## Source lifecycle and ordering

- **Typed outcomes.** Propose an enumeration result of `ok` with a possibly empty source list, `cancelled`, or `error`. A start request returns either `accepted` with an attempt token or a typed failure; acceptance means only that startup was requested, not that capture is running. Stable failure categories should include `not_found`, `permission_denied`, `unsupported`, `busy`, `device_lost`, `cancelled`, and `backend_error`, with an optional backend-specific diagnostic kept off the callback. An empty list is not an error, and an error message is not a machine-readable category. PR #28 defines typed enumeration, start and status results; native adapters still need integration.
- **Single control authority.** One control owner serializes start, stop, source switching and backend state notifications. Each notification carries the start-attempt token and an ordering number assigned by an adapter-owned serial dispatcher that preserves the backend's causal transitions; discard notifications from older attempts or at or below the last accepted number, and fail closed on an unexplained sequence gap. If native callbacks are concurrent, the adapter must establish that order explicitly; numbering events only when they happen to arrive at the consumer does not recover lost causal order. PR #28 adds per-attempt sequence validation to `SourceLifecycle`; adapters must establish causal order before assigning numbers and handle delivery loss. Backend threads may transfer notifications to the control owner, but neither blocking nor allocation is allowed in the audio callback.
- **Bounded delivery and loss.** PCM stays in the preallocated SPSC audio queue. Control delivery may use a separate bounded mechanism appropriate to its actual producer count; it must not assume SPSC if multiple backend threads can write. Overflow must be observable and fail closed: invalidate active evidence, report a control-delivery error or interruption, quiesce/restart as needed, and reacquire. Do not silently discard an interruption/error and continue presenting old values. Separate queues do not automatically order control and PCM: tag blocks with epoch/position and prevent acceptance of new-epoch data until the worker has installed its format and reset boundary. Drop late old-epoch data.
- **Epoch owner.** The process-level source coordinator allocates strictly increasing `uint64_t` epochs for each new stream, restart, device/format change or file seek, including when a source object is recreated. Values are never reused while publications from the process session can remain in flight; exhaustion is an explicit error, not wraparound. Across process restarts, a separate session identity or a proven drain prevents old persisted/queued notifications from matching. `SourceAttempt` identifies a start attempt and is not an epoch. On `stop`, invalidate the attempt and quiesce callbacks before releasing buffers; the worker drops or drains old queued blocks before accepting a new epoch.
- **Time and reacquisition.** Positions count complete frames from an epoch-local origin; format changes require a fresh epoch. A live backend reports whether an anchor is valid, its clock domain, and known uncertainty/latency; an unavailable anchor is absent, not zero. PR #28 represents absent anchors with an optional value and adds domain, uncertainty and latency metadata; actual backend measurements remain open. An interruption, gap, dropped block or clock reset invalidates affected tracker evidence and publication; analysis reacquires before reporting fresh live estimates.

## Jobs, cache and cancellation

- **Typed outcomes.** Propose `find`: `hit`, `miss`, `cancelled`, or `error`; and `publish`: `committed`, `cancelled`, `stale_input`, or `error`, with a diagnostic for failures. A cache miss is not a database error and a cancelled operation is not a miss. PR #30 defines these typed outcomes, a verifier and run-ID recovery interface; database implementation and same-source verification remain open.
- **Identity and revalidation.** Cache keys include validated content identity, engine/algorithm versions, configuration and offline/live mode, not path alone. The worker retains evidence of the opened source and its pre-analysis attributes, computes/validates its content identity, then rechecks the file version before publishing. If the input changed or cannot be reliably matched, return `stale_input` and preserve the old active result. A stat/hash check alone cannot prove immunity to every concurrent modification: document the platform's remaining race and use stronger file identity/locking where available; do not claim guarantees the filesystem does not supply.
- **One commit point.** A database worker owns connections and serializes publication. It stages the completed result and rechecks identity/version inside the publication operation, then atomically swaps the active completed result in a SQLite transaction. Cancellation observed by that worker **before it starts commit** rolls back and returns `cancelled`; once commit begins, the worker resolves the operation as committed or error, rather than reporting cancellation for a committed replacement. Later cancellation is too late to undo a successful commit. The existing `JobLifecycle` expresses the resulting worker-serialized terminal state but cannot itself enforce the transaction or arbitrate a simultaneous request.
- **Crash and ambiguous commit.** Never mark a job complete before successful commit. A rollback or failure keeps the prior active result; recovery marks incomplete runs retryable. If the process/connection fails while commit outcome is unknown, report an indeterminate storage error and recover by querying a unique run ID after reopening; do not claim either rollback or success without evidence. Test cancellation on both sides of the commit decision, file changes, failed commits, restart/recovery, and unchanged-file cache reuse. No SQL work runs on GUI or capture threads.

## Estimators, snapshots and presentation

- **Worker ownership and causality.** One analysis worker owns each estimator instance. It consumes borrowed PCM synchronously and retains only owned data. Live analysis sees only observed samples, identifies any deliberate look-ahead as delay, and resets on epoch/format changes or gaps. Exceptions/errors are translated to an explicit error state off the callback. An empty candidate list or absent BPM means unknown, and scores are uncalibrated strengths, not probabilities. The current tempo implementation does not yet implement all strategy ports or timestamp beats.
- **Frame boundaries (merged in PR #21).** The `observed_through` boundary is exclusive: a block beginning at frame `f` with `n` frames observes `[f, f+n)`; beats must be `< observed_through`, and chord intervals are nonempty half-open `[start, end)` with `end <= observed_through`. `SnapshotPublisher` enforces these boundaries with regression tests. Publication monotonic time and analysis delay stay distinct from event frame time.
- **Invalidation and UI delivery.** On stop, silence, interruption, error, expiry or discontinuity, the analysis owner invalidates its `TrackingMachine` token and clears `SnapshotPublisher` before accepting new evidence; queued results bearing an old token must be rejected. The UI must receive a revisioned clear on its own thread and clear displayed labels when it applies it. `PresentationGate` rejects older revisions, but neither it nor a shared pointer revokes a copy already displayed; a clear cannot take effect before delivery. The producer assigns one monotonically increasing revision to every snapshot and clear, including across restarts; on overflow it stops instead of wrapping. A bounded/coalescing handoff must retain the latest revision **including clears** and must not let a delayed older snapshot revive the display. If the gate/producer is recreated, drain old messages or add an external session identity. GUI objects stay on the GUI thread; Qt types stay out of core.
- **Verification at integration.** Exercise delayed old result after clear, clear arriving after a newer snapshot, queue overflow, restart/seek/silence/resume, frame-boundary validation and immutable reader copies; then add real backend and GUI scenarios. Synthetic or fake tests prove boundary behavior only, not native device or overlay qualification.

## Proposed Phase 1 SQLite increment

A private prototype proposes schema version 1 with `runs` keyed by a caller-provided run ID and an `active` mapping keyed by content identity, engine version, configuration and mode. A foreign key constrains active entries to matching completed runs. Version 0 creates the schema transactionally; unknown versions fail closed. On open, unfinished runs become retryable. Publication revalidates through a worker-supplied callback and swaps the active entry in a transaction. Cancellation checked immediately before COMMIT rolls back; after COMMIT starts its result is authoritative unless an error leaves the outcome ambiguous. This schema and API require integration-owner review and are not used by the product.

The prototype deliberately does not establish safe content identity: no hash, opened-file evidence, file version, or reliable revalidation implementation exists yet. A caller callback is not a substitute for those. SQLite errors are currently collapsed into `error`; unknown COMMIT outcomes require reopening and querying the run ID. The result is an opaque blob, with no finalized serialization, track metadata, beat or chord schema. A file-backed cache holds an SQLite exclusive lock for its lifetime; concurrent connections cannot open the store while that owner is alive. This prevents recovery from reclassifying another owner's running jobs, but prevents simultaneous readers and requires reliable filesystem locking. The bounded executor has one worker, stable priority and a bounded waiting queue; shutdown cooperatively stops active work and discards waiting jobs, but does not yet report per-job cancellation or failures. SQLite is an unpinned host development dependency. These gaps block product use and Phase 1 acceptance.

## File evidence and tempo job proposal

The optional private file job hashes the full input with SHA-256 before lookup and again after a cache miss is analyzed. The cache key uses the digest, caller-supplied engine/configuration versions, and offline mode; a hit skips the tempo replay. Hashing occurs on each requested job rather than scanning an entire collection on launch. Decoding uses the existing real libsndfile/aubio replay, with cooperative stop and frame-progress callbacks between blocks. The result format currently stores only the preliminary tempo result, not key or chords. OpenSSL is a host dependency in this prototype and is not yet pinned for release.

The decoder opens the path separately from the hasher. A change and restoration between observations, or concurrent replacement during decoding, can evade these checks; equal pre/post hashes do not prove that the decoder saw those same bytes. Therefore this path is not yet eligible for user-facing publication. A decoder API that consumes the same opened file or a securely created immutable snapshot, plus platform-specific identity/revalidation, needs coordinator and DSP review. There is also no saved-attribute fast path, per-job queue handle, complete retry status/diagnostics, durable run-ID reconciliation after an indeterminate commit, or integration with the accepted shared store contract.

Review of proposed PR #30: typed outcomes and commit boundary are compatible in principle, but the proposed `publish(before, after, ...)` signature provides no mechanism to recheck the open input inside the transaction and neither its inputs nor outputs expose the unique run ID needed to reconcile an indeterminate commit. `FileVersion` also lacks opened-file identity and a specified clock/epoch for `modified_ns`; the proposed four cache identity fields do not separately name algorithm versions beyond what callers may encode in `engine_version`. Resolve these contracts before treating the private implementation as an `AnalysisStore` adapter.

The later proposed unique run ID plus worker-invoked verifier addresses the two immediate API gaps if the verifier is bound to the exact bytes consumed by the decoder and stays alive through publication. The current `FileReader` only opens a path internally and does not expose or accept the hash stream's handle, so a same-source verifier cannot yet be implemented against it. The API also needs a lookup/reconciliation operation for a run ID after an ambiguous commit, and must specify whether verifier I/O error maps to error while changed or unprovable evidence maps to stale input. Do not let a callback that only re-stats the path claim same-opened-source verification.

## Decoder handle proposal for opened-source verification

The DSP and integration owners should review a decoder constructor or factory that takes ownership of a seekable read-only source handle (or a lifetime-bound virtual-I/O object), rather than reopening a path. Its contract must define ownership, close/quiescence, seek/read errors, thread confinement, and source lifetime through replay. Merely passing the original mutable handle does not prove consistent bytes if another writer changes it during decoding.

Proposed safe direction: on the library worker, open the source without write access, retain its OS file identity and attributes, stream it into a securely created private temporary snapshot using bounded memory while hashing, and decode that exact snapshot through the handle boundary. Before committing, re-read/hash and check the retained source and verify that the indexed path still names the intended source. Reject changed or unprovable evidence. The snapshot must have exclusive creation, restrictive permissions, deterministic cleanup on all exits, no source modification, and platform-specific tests; its lifetime must cover the decoder and verifier. File locking and identity availability vary by filesystem; even a final check cannot eliminate a write after verification. Explicitly document the residual check-to-commit and path-replacement windows and do not claim immunity to concurrent writers. An integration owner must approve the handle/identity contract and DSP must own the decoder changes. Current path-based `replay_file` does not meet this contract.

The worker prototype now retains a run ID and full cache key on publication errors. After closing and reopening the exclusively owned database, `recover` looks up the exact run: a completed row is proof that transaction committed, including when a newer result is active; an interrupted row is marked retryable; absence is reported separately. Recovery itself can fail and must not turn that failure into a claimed outcome. This remains private and must be reconciled with the shared contract. The bounded queue's tracked handles expose cooperative individual cancellation and monotonic decoded-frame progress; queued cancellation changes its state immediately but retains queue capacity until the worker or shutdown removes it. A running job supplies its terminal result, so cancellation after its commit decision cannot relabel completion.

### Snapshot handoff and verifier requirements

The job owns a securely and exclusively created private snapshot. Finalize it by closing every write-capable handle, then hash the finalized bytes and lend the same seekable, read-only byte source to the decoder. No independent path reopen or path fingerprint establishes that the decoder consumed those bytes. The byte-source contract must prevent writes through its API and prevent outside writers from obtaining a writable handle under the platform's actual access-control and sharing rules; if that cannot be established, fail closed. Hashing and decoding may use independent read cursors only if both are bound to the same immutable snapshot object. Ensure the decoder does not close a borrowed underlying handle or retain the byte source beyond its documented lifetime.

The job retains the original opened-source identity and evidence through the publication decision. On the owning worker, the verifier checks both the retained original and the current path-to-original binding, comparing the original's contents against the snapshot evidence. Verify before accepting a cache hit as well as before publishing a new result. Report changed or unprovable identity as stale, filesystem or I/O failure as error, and never substitute a path-only hash for an opened-source match. Neither an open handle nor a pre/post hash excludes all external writes, path changes, or the final verification-to-commit race; document filesystem-specific residual limits and use available stronger coordination. Do not treat an untrusted temporary pathname as identity.

The snapshot owner outlives every decoder, virtual-I/O callback, verifier and pending read; destroy/quiesce the decoder before closing or deleting the snapshot, including cancellation and exception paths. Operations on a decoder and a shared seek cursor stay on its owning analysis worker; a database worker may invoke the verifier only after ownership has been transferred or through an explicitly synchronized worker handoff. The verifier must not touch a decoder concurrently, and no blocking I/O belongs on the GUI or capture callback. If hash and decode require different workers, give each an independently positioned read handle to the same finalized object, with OS-backed identity validation and explicit lifetime, rather than sharing a mutable cursor.

The verifier should accept the job's stop token: rehashing large inputs may be slow, and it must check cancellation between bounded reads and before returning. An in-flight blocking read may finish first. Return a distinct cancelled outcome; cancellation observed before the database worker starts COMMIT rolls back and yields cancelled, while cancellation after that decision cannot replace the commit outcome. The verifier must never report cancellation as changed input or as a successful match. Stop-token delivery alone does not serialize the commit decision; the database worker owns that decision. The current `FileReader` opens a path via libsndfile and exposes neither a borrowed seekable byte source nor a same-source verifier, so this contract needs DSP and integration changes before the proposed safe path can be implemented.

The POSIX snapshot prototype creates a mode-0600 unique temporary, writes a bounded copy, restricts permissions, reopens the same inode read-only, unlinks its temporary name and hashes those finalized bytes. It retains the original descriptor, verifies device/inode, size and high-resolution modification/change times and rehashes the retained original while also checking the path binding. The borrowed descriptor remains owned by the snapshot. This is a staging primitive, not a guarantee against a same-user process obtaining a writable handle while the temporary name is visible, hostile filesystem behavior, or writes/replacement after final verification. It is not yet bound to the decoder or exposed to product. Windows currently returns unverifiable; macOS has not been tested.

For the proposed `ByteSource`, fixed length and `read_at` are compatible with a private snapshot provided the contract explicitly requires immutable bytes for its entire borrowed lifetime, not merely fixed length. Define overflow and EOF behavior, disallow returning more bytes than the span, describe short reads and errors, require a nonzero data result, and define cancellation without advancing a cursor on cancelled/error results. A single `ByteCursor` must be worker-confined; the source must declare whether concurrent `read_at` is supported and how outstanding reads quiesce before destruction. The decoder must not retain it after destruction or close its borrowed descriptor. If source construction cannot guarantee immutability or identity, fail closed; hashing a separate pathname does not satisfy this contract. Cancellation should flow through each bounded read and verification, with the worker deciding the commit boundary after the verifier returns.

Review of PR #41: the proposed `ByteSource`/`ByteCursor` provides the needed sequential borrowed-lifetime boundary, validates nonzero in-range reads and premature EOF, and correctly confines a source and cursor to one worker. No additional concurrent-read guarantee is needed if hashing, decoding and verification are serialized. The contract should explicitly define the source's behavior for an empty output span and whether cancellation wins over EOF for direct `read_at` callers; the cursor already rejects an empty span and checks cancellation first. Clarify that immutable bytes and fixed size must hold for the entire lifetime, that any `size()` error/exception propagates without advancing, and that a source reporting cancellation/error must not have changed the caller-visible cursor. An immutable source does not prove the original path still binds to the retained original: that remains a separate verifier operation.

The libsndfile virtual-I/O adapter needs signed `sf_count_t` bounds checks for size, offset and `SEEK_SET`/`SEEK_CUR`/`SEEK_END`, overflow-safe conversion, and an explicit mapping of failed or cancelled callbacks to a decoder error/cancellation after the native call returns. Its callbacks must use the same live `ByteSource` object, never throw through C, and must not close a borrowed descriptor; destroy the SNDFILE and quiesce callbacks before releasing the byte source or snapshot. Carry the stop token through adapter state because native callbacks do not accept it directly. A blocking native read is not automatically interruptible. Native integration tests on Linux, macOS and Windows should exercise real decoder output from the same snapshot source, non-ASCII original paths, short/error/cancelled reads, seek boundaries, source modification/replacement and cleanup; verify source audio hashes unchanged. PR #41 is provisional and it is used only in the isolated integration branch.

A mutation-and-restoration test observed both outcomes across runs: change-time metadata can coincide at filesystem timestamp resolution, so restoring bytes and modification time may leave the original indistinguishable to this verifier. The descriptor-backed snapshot still supplies the same bytes to the decoder, but the verifier cannot prove that no intervening write occurred. Do not claim ABA detection, immutable-source proof, or final check-to-commit immunity. Stronger platform-specific snapshot/seal and file-identity mechanisms require review before product use.


At PR #30 (`98be006c97445f987acea8ab16eea57372aaab89`), `FileVersionVerifier::verify()` had no stop token or cancelled outcome. PR #46 has since added both, and the private snapshot verifier is now adapted to the shared interface. The shared contract also describes revalidating the same opened input used for analysis, while the snapshot proposal decodes an immutable copy and verifies the separately retained original plus path binding; this distinction needs an explicit shared contract revision. The shared recovery API queries only run ID and returns committed/not_found/error, whereas the private implementation additionally checks the key and exposes retryable; an adapter must specify how it maps retryable to not_found and preserves enough durable run evidence. The recovery mapping and snapshot/original distinction still need integration-owner review.

## Windows snapshot candidate

The private snapshot now has a Windows implementation for review. It opens the original read-only with sharing that allows replacement detection, records volume and 128-bit file ID plus size and basic timestamps, creates a random `CREATE_NEW` temporary with delete-on-close and write sharing denied, copies and hashes in bounded chunks, duplicates a read-only handle, closes the writer, and hashes the retained copy. The object retains both handles; `read_at` is worker-confined and cancellation is cooperative. Revalidation hashes the retained original and checks the current path binding. Filesystems that do not provide the required ID information return an error; no identity guarantee is invented. The tests use native Windows, but same-user process-handle attacks, non-NTFS/network filesystem semantics, original mutation/restoration and the last verification-to-commit window remain limitations. This earlier candidate was not connected to a decoder or store; the later isolated integration below exercises `ByteSource` and `AnalysisStore`, but no application workflow uses it.

Review before PR #46 merged: its distinct verifier cancellation outcome and stop token map naturally to `SnapshotStatus::cancelled`; cancellation remains a worker-serialized decision before COMMIT. The shared language still needs to distinguish the immutable decoded snapshot from the separately retained original and path binding. File ID, path binding and snapshot lifetime remain backend/platform responsibilities. The merged contract is now used by the private adapter.

## Review of current ByteSource PR #41 against this integration

The proposed `ByteSource`/`ByteCursor` shape is sufficient for the isolated integration: `SnapshotSource` borrows one job-owned finalized snapshot, reports its fixed length, maps bounded offset reads and cancellation, and remains alive through `VirtualFileReader` destruction. The snapshot's digest is computed by reading that same retained snapshot object before the decoder borrows it; the original handle and path are separately revalidated. This is exercised with actual libsndfile/aubio output, cancellation while copying/decoding, and source replacement or mutation during analysis. Tests also cover old-result preservation and cache reuse. A real cancellation injected between original-file rehash chunks is exercised, including propagation through the merged verifier contract while preserving an earlier cached result.

Before treating #41 as a stable contract, clarify direct `read_at` precedence for an empty span and for a pre-cancelled token at EOF, and explicitly say that the caller's output buffer may have been modified even when cancellation or error returns zero bytes. The existing cursor checks a pre-cancelled token first and rejects empty spans; this private adapter follows that behavior. The source must remain byte-immutable and alive until all decoder callbacks have quiesced; #41 deliberately does not enforce that guarantee. Linux now requires anonymous `O_TMPFILE` plus `/proc/self/fd` and fails closed if unavailable, while the Windows candidate denies write sharing and uses delete-on-close. Same-user process-handle access, filesystems with weaker semantics, macOS named temporaries, mutation/restoration, and the final source-verification-to-commit interval remain limitations. Do not infer native desktop/audio qualification or enable the product path from these tests.

Merged verifier cancellation #46 is used in this branch: `verify(stop_token)` maps `cancelled`, `changed`/`unverifiable`, and I/O errors separately; the store returns a committed result before considering later cancellation. The shared wording still needs to distinguish the decoded immutable snapshot from the separately retained original/path being verified. This branch now feeds DSP's proposed shared tempo replay; a combined tonal/beat replay and final interface approval remain outstanding. The private collection schema/query contract is a proposal for UI/integration review, not an accepted public API.

Snapshot copies use bounded memory but can consume temporary disk space proportional to the source file. A storage quota/free-space policy, cleanup after abnormal termination for named-platform temporaries, and user-facing failure behavior are required before product enablement. The experimental collection queries return metadata only; they do not yet expose validated BPM/key/chord details or populate a Qt model. A detail view must run the snapshot validation/store path on a worker before treating a stored content hash or cached result as current.

Its `ByteSource` and `ByteCursor` method implementations are unchanged from the version exercised here; there is no remaining concrete interface blocker for this private integration. This is not an approval of the snapshot's filesystem guarantees or of product/native qualification.

A transaction must stage all records and reverify before publication, preserving the previous active result on failure/cancellation; a failed acknowledgement needs run-ID recovery. Because event vectors can grow with file duration, require explicit storage/decoder limits and bounded paged detail retrieval (including stable ordering and cancellation), not an unbounded GUI payload. Define source-content identity and schema migration/unsupported-version handling before implementing storage. None of this closes snapshot mutation/restoration or verification-to-commit races; product use stays gated.

UI worker boundary: `entries(query, completion)`, `detail(path, completion)`, `analyze(path, engine, configuration, epoch, completion)`, and `lookup(path, exact AnalysisIdentity, epoch, completion)` return a shared `Ticket`. Its thread-safe `result()` retains the terminal owned `Result` after supersession, cancellation or bridge destruction; an empty optional means not terminal. Pending cancellation is retained as `Result.cancelled`, while active analysis retains its actual typed `FileJobStatus`, including a commit that wins over cancellation. The bridge suppresses callbacks for superseded/cancelled requests, and the dispatcher must enqueue callbacks on the GUI thread. Lookup snapshots the path, requires the digest to match the supplied complete identity, finds that exact key, revalidates and returns `LookupStatus::{hit,miss,changed,cancelled,error}`; hits are rebound to the caller's nonzero epoch. This is evidence under the existing documented platform races, not a freshness guarantee after delivery. It does not analyze on miss. A single global request lane remains experimental, so UI owners must decide whether independent views need separate lanes.

Storage review of #57 at `d896c709a57db2da268b22f1954ee3ee198180ef`: its separate value has the needed mode, boundaries, optional beat strength, overlapping windows and independent rolling-key start, and deliberately leaves persistence unspecified. Storage still needs canonical, duplicate-free component/version ordering and an unambiguous complete configuration identity including library versions/profile/downmix/window/hop; checked conversion of unsigned frame positions/counts to SQLite's signed integer range; limits on total serialized bytes as well as counts and per-field text; deterministic tie-breaks for equal event positions and stable run-scoped paged reads; and a versioned migration/unknown-format policy. Session epochs should be rebound consistently on retrieval, not included in content identity. A structurally valid value does not prove source identity or authorize publication. The existing tempo-only serializer cannot store #57 and must not silently discard its fields.

Concrete offline storage review, pending #57 approval: keep a versioned result header tied to a unique completed run and a content hash plus canonical mode, engine, configuration and ordered component versions. Store tempo and validated-track-key optionals in the header and beats and tonal windows in separate run-owned ordered rows. Each beat row preserves its event frame, emission boundary and nullable strength; each window row preserves start, exclusive end, nullable rolling-key start, and nullable key/chord labels and strengths. Presence flags or SQL NULL must distinguish absence from a real zero score. No output is widened into a whole-track estimate or segment. Every insertion is staged and structurally validated with checked unsigned-to-SQLite conversion and explicit aggregate byte/event limits; any limit, validation, cancellation or identity error rolls back and preserves the prior active run. Revalidate the retained source immediately before the atomic active-run switch and retain run-ID recovery for an indeterminate commit; the documented filesystem race remains.

For UI detail, return a copied header and bounded pages (maximum page size to be agreed) identified by immutable completed run ID, event kind and an ordinal cursor; order equal-time events by ordinal. Each page includes run identity and next cursor, is cancellable, and is revalidated before presenting a source-bound result. Keep the referenced run available for the lifetime of paging, or explicitly return an expired-run outcome; a replacement active run must never splice pages from two analyses. Rebind all returned positions to the same nonzero coordinator-issued session epoch; epochs are not content/cache identity. Bound total query response bytes as well as rows. Decide page retention, full identity encoding and validation limits with the DSP and UI owners before schema migration. #57 is still a draft; neither its types nor this schema are implemented or used by this branch.

The worker bridge now has independent browse and analysis cancellation/generation lanes, each with one pending request, scheduled fairly on the same database worker. A browse can wait behind long analysis I/O but cannot cancel it; `cancel_browse()`, `cancel_analysis()` and `cancel()` have explicit scope. `analyze_indexed(key, path, engine, configuration, epoch, completion)` requires an existing entry and matching normalized path, runs real snapshot tempo analysis and then records its content hash in that row after a hit or commit. The index association is a separate SQLite write, not atomic with publication; `Result.association_error` preserves a successful analysis outcome while reporting update failure. `lookup_indexed(key, path, engine, configuration, epoch, completion)` reads that hash, resolves the active run for the exact tempo algorithm/configuration identity, snapshots and revalidates the source before returning an owned typed result; absent rows/hashes return miss. The hash is evidence, not a permanent freshness guarantee, and an identity change returns changed. Path keys must be caller-normalized UTF-8 and lexically match the supplied path; platform-specific aliases and case folding are not resolved here. Both methods return retained tickets and deliver only through the GUI dispatcher. Existing filesystem races and product gates remain.

The experimental offline integration branch implements a versioned archive and bounded owned pages on the library worker, but does not wire the non-cacheable #58/#60 producer. The UI-facing `offline_page` derives source evidence from a fresh snapshot, checks the indexed hash and complete requested key, and returns a page tied to the current run or changed if that run was replaced. It decodes a full, 8 MiB maximum archive per request, rather than streaming events; per-kind page counts are limited to 200. `analyze_indexed` now atomically switches the active tempo result and index hash on cache misses; a cache hit is separately verified and associated transactionally. Publication requires trustworthy runtime identity from its caller, which remains unestablished for the composite producer; do not enable product caching.

PR #63 proposes a process-owned atomic epoch allocator. This integration currently accepts caller-issued nonzero epochs for jobs and returned pages and does not own an allocator. On adoption, the application coordinator must retain and inject one allocator into live and library control paths, issue a fresh epoch for every new analysis session and each seek/discontinuity, and fail the operation without publishing if allocation is exhausted. The virtual decoder must receive the newly issued epoch before seek; worker completion order must not be used as epoch order. No allocation belongs in the capture callback, and separate per-worker allocators are not safe. Cross-process persisted epochs are rebound; process-session identity/drain must be addressed by the coordinator. This is a review plan, not an adopted shared contract.

The subsequent combined review branch exposes `LibraryBridge::analyze_composite(path, epoch, completion)` only when private music replay is enabled. It returns #60's real snapshot-backed, owned `CompositeJobResult` on the existing analysis lane with explicit non-cacheable status; it never calls `OfflineArchive::publish`. The current private archive trusts caller-provided identity and cannot prove loaded library artifacts, so filling invented identity strings is not an acceptable way to enable caching. Coordinator ownership and verified runtime identity, Essentia factory serialization, page/UI policy and source filesystem guarantees remain prerequisites.
