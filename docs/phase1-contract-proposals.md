# Proposed initial Phase 1 contract decisions

**Review status:** proposed for integration-owner acceptance; these are not yet implemented guarantees or replacements for the current headers. The owner owns `include/beatglass/`, result and database schemas, root CMake, dependency definitions and CI. Agents may implement behind private adapters in isolated worktrees, but must propose shared API/schema changes before another workstream depends on them. See [foundation ownership](foundation-handoff.md). The real CLI currently produces tempo only; no proposal below implies that capture, storage, key, chords or the UI pipeline already work.

## Source lifecycle and ordering

- **Typed outcomes.** Propose an enumeration result of `ok` with a possibly empty source list, `cancelled`, or `error`. A start request returns either `accepted` with an attempt token or a typed failure; acceptance means only that startup was requested, not that capture is running. Stable failure categories should include `not_found`, `permission_denied`, `unsupported`, `busy`, `device_lost`, `cancelled`, and `backend_error`, with an optional backend-specific diagnostic kept off the callback. An empty list is not an error, and an error message is not a machine-readable category. Exact API names and representation require integration approval: today's `AudioSource::enumerate/start/status` cannot express all of these outcomes.
- **Single control authority.** One control owner serializes start, stop, source switching and backend state notifications. Each notification carries the start-attempt token and an ordering number assigned by an adapter-owned serial dispatcher that preserves the backend's causal transitions; discard notifications from older attempts or at or below the last accepted number, and fail closed on an unexplained sequence gap. If native callbacks are concurrent, the adapter must establish that order explicitly; numbering events only when they happen to arrive at the consumer does not recover lost causal order. The current `SourceLifecycle` rejects old attempts but does **not** order notifications within an attempt; adapters cannot assume it does. Backend threads may transfer notifications to the control owner, but neither blocking nor allocation is allowed in the audio callback.
- **Bounded delivery and loss.** PCM stays in the preallocated SPSC audio queue. Control delivery may use a separate bounded mechanism appropriate to its actual producer count; it must not assume SPSC if multiple backend threads can write. Overflow must be observable and fail closed: invalidate active evidence, report a control-delivery error or interruption, quiesce/restart as needed, and reacquire. Do not silently discard an interruption/error and continue presenting old values. Separate queues do not automatically order control and PCM: tag blocks with epoch/position and prevent acceptance of new-epoch data until the worker has installed its format and reset boundary. Drop late old-epoch data.
- **Epoch owner.** The process-level source coordinator allocates strictly increasing `uint64_t` epochs for each new stream, restart, device/format change or file seek, including when a source object is recreated. Values are never reused while publications from the process session can remain in flight; exhaustion is an explicit error, not wraparound. Across process restarts, a separate session identity or a proven drain prevents old persisted/queued notifications from matching. `SourceAttempt` identifies a start attempt and is not an epoch. On `stop`, invalidate the attempt and quiesce callbacks before releasing buffers; the worker drops or drains old queued blocks before accepting a new epoch.
- **Time and reacquisition.** Positions count complete frames from an epoch-local origin; format changes require a fresh epoch. A live backend reports whether an anchor is valid, its clock domain, and known uncertainty/latency; an unavailable anchor is absent, not zero. The present `AudioClockAnchor` is a point estimate and has no validity/uncertainty field. An interruption, gap, dropped block or clock reset invalidates affected tracker evidence and publication; analysis reacquires before reporting fresh live estimates.

## Jobs, cache and cancellation

- **Typed outcomes.** Propose `find`: `hit`, `miss`, `cancelled`, or `error`; and `publish`: `committed`, `cancelled`, `stale_input`, or `error`, with a diagnostic for failures. A cache miss is not a database error and a cancelled operation is not a miss. Today's optional/bool `AnalysisStore` interface does not encode these distinctions and must be revised centrally before cross-module callers depend on them.
- **Identity and revalidation.** Cache keys include validated content identity, engine/algorithm versions, configuration and offline/live mode, not path alone. The worker retains evidence of the opened source and its pre-analysis attributes, computes/validates its content identity, then rechecks the file version before publishing. If the input changed or cannot be reliably matched, return `stale_input` and preserve the old active result. A stat/hash check alone cannot prove immunity to every concurrent modification: document the platform's remaining race and use stronger file identity/locking where available; do not claim guarantees the filesystem does not supply.
- **One commit point.** A database worker owns connections and serializes publication. It stages the completed result and rechecks identity/version inside the publication operation, then atomically swaps the active completed result in a SQLite transaction. Cancellation observed by that worker **before it starts commit** rolls back and returns `cancelled`; once commit begins, the worker resolves the operation as committed or error, rather than reporting cancellation for a committed replacement. Later cancellation is too late to undo a successful commit. The existing `JobLifecycle` expresses the resulting worker-serialized terminal state but cannot itself enforce the transaction or arbitrate a simultaneous request.
- **Crash and ambiguous commit.** Never mark a job complete before successful commit. A rollback or failure keeps the prior active result; recovery marks incomplete runs retryable. If the process/connection fails while commit outcome is unknown, report an indeterminate storage error and recover by querying a unique run ID after reopening; do not claim either rollback or success without evidence. Test cancellation on both sides of the commit decision, file changes, failed commits, restart/recovery, and unchanged-file cache reuse. No SQL work runs on GUI or capture threads.

## Estimators, snapshots and presentation

- **Worker ownership and causality.** One analysis worker owns each estimator instance. It consumes borrowed PCM synchronously and retains only owned data. Live analysis sees only observed samples, identifies any deliberate look-ahead as delay, and resets on epoch/format changes or gaps. Exceptions/errors are translated to an explicit error state off the callback. An empty candidate list or absent BPM means unknown, and scores are uncalibrated strengths, not probabilities. The current tempo implementation does not yet implement all strategy ports or timestamp beats.
- **Proposed frame boundaries.** Use an exclusive `observed_through` boundary: a block beginning at frame `f` with `n` frames observes `[f, f+n)`; beats must be `< observed_through`, and chord intervals should be nonempty half-open `[start, end)` with `end <= observed_through`. This is a proposed contract change: the current `SnapshotPublisher` permits a beat at `observed_through` and zero-length chords. Do not make independent assumptions until integration approves the shared-header change and adds boundary regression tests. Publication monotonic time and analysis delay stay distinct from event frame time.
- **Invalidation and UI delivery.** On stop, silence, interruption, error, expiry or discontinuity, the analysis owner invalidates its `TrackingMachine` token and clears `SnapshotPublisher` before accepting new evidence; queued results bearing an old token must be rejected. The UI must receive a revisioned clear on its own thread and clear displayed labels when it applies it. `PresentationGate` rejects older revisions, but neither it nor a shared pointer revokes a copy already displayed; a clear cannot take effect before delivery. The producer assigns one monotonically increasing revision to every snapshot and clear, including across restarts; on overflow it stops instead of wrapping. A bounded/coalescing handoff must retain the latest revision **including clears** and must not let a delayed older snapshot revive the display. If the gate/producer is recreated, drain old messages or add an external session identity. GUI objects stay on the GUI thread; Qt types stay out of core.
- **Verification at integration.** Exercise delayed old result after clear, clear arriving after a newer snapshot, queue overflow, restart/seek/silence/resume, frame-boundary validation and immutable reader copies; then add real backend and GUI scenarios. Synthetic or fake tests prove boundary behavior only, not native device or overlay qualification.

## Suggested initial ownership and decisions

Integration owner decides and versions these contracts, shared headers, schema, root build, dependencies and CI. DSP owns `lib/core/`, file replay and CLI; library owns `lib/library/`; shared UI owns `src/desktop/` and QML; each platform owner owns its assigned `lib/capture/<platform>/` and native-window files. Tests for each module remain under `tests/`; separate worktrees use a declared base commit. Approve the four proposed decisions above before cross-module integration relies on them; allow independent implementations and test fixtures to proceed under the documented boundaries. Phase 0 exit and release qualification decisions remain with the integration owner.

## Proposed Phase 1 SQLite increment

A private prototype proposes schema version 1 with `runs` keyed by a caller-provided run ID and an `active` mapping keyed by content identity, engine version, configuration and mode. A foreign key constrains active entries to matching completed runs. Version 0 creates the schema transactionally; unknown versions fail closed. On open, unfinished runs become retryable. Publication revalidates through a worker-supplied callback and swaps the active entry in a transaction. Cancellation checked immediately before COMMIT rolls back; after COMMIT starts its result is authoritative unless an error leaves the outcome ambiguous. This schema and API require integration-owner review and are not used by the product.

The prototype deliberately does not establish safe content identity: no hash, opened-file evidence, file version, or reliable revalidation implementation exists yet. A caller callback is not a substitute for those. SQLite errors are currently collapsed into `error`; unknown COMMIT outcomes require reopening and querying the run ID. The result is an opaque blob, with no finalized serialization, track metadata, beat or chord schema. A file-backed cache holds an SQLite exclusive lock for its lifetime; concurrent connections cannot open the store while that owner is alive. This prevents recovery from reclassifying another owner's running jobs, but prevents simultaneous readers and requires reliable filesystem locking. The bounded executor has one worker, stable priority and a bounded waiting queue; shutdown cooperatively stops active work and discards waiting jobs, but does not yet report per-job cancellation or failures. SQLite is an unpinned host development dependency. These gaps block product use and Phase 1 acceptance.
