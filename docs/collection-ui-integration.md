# SQLite collection UI integration proposal

The filesystem browser is a view of a directory, not an indexed collection. The accepted AnalysisStore contract supplies typed cache lookup and publication outcomes, but does not expose a collection query; the library backend prototype does not yet supply completed result serialization. Before connecting a collection table, the integration owner and library backend should agree on a worker-owned query API returning immutable, bounded pages with stable track identity, path/availability, metadata, analysis status and typed error/cancellation outcomes. Filter and sort requests need explicit ordering, request generations and cancellation or stale-response rejection; SQLite work stays off the GUI thread. Results should identify the source file version and analysis configuration so selecting a row cannot silently display a prior file version's result. A missing or moved file remains a visible entry with a recoverable status, and removing an entry must not delete the source.

A selected result needs its own immutable detail value with sample rate, epoch or file identity, exclusive observed frame boundary, nonempty half-open chord segments, beat positions and explicit unknown values. Playback position is in milliseconds from Qt Multimedia; convert carefully to sample frames using the result's sample rate, clamp only for display, and clear the detail view when the selected file/version changes. The player and analysis decoder may support different formats and must report their own errors. Playback/seek must remain optional and must not be used as evidence that the analysis or cached result exists. A worker-to-GUI delivery contract must define ordering, bounded updates, shutdown, and session identity across reconnects. User audio and tags remain read-only.

The current backend prototype does not meet these requirements and no UI call depends on this proposal. End-to-end tests should cover real indexing, unchanged-file reuse across restart, modified/missing files, stale asynchronous responses, result identity, cancellation, and seeking across half-open timeline boundaries. Native audio and GUI qualification remains separate.

## Proposed first query and detail handoff (not yet accepted)

The UI needs a worker request keyed by a session and monotonically increasing request ID, with search text, an explicitly selected sort field/direction, and a bounded page cursor. A successful page contains stable track IDs, display title/artist or explicit absence, path, availability, optional duration, optional BPM/key, and analysis state. Miss/empty, cancellation and error remain distinct. A cursor must either hold a consistent query snapshot or report invalidation; the UI discards results for older request IDs and clears selection if its track/version is removed or replaced.

A detail request takes the stable track ID and the active run ID or version token returned by the page. Its response includes that identity, sample rate, track duration, status, optional BPM/key candidates, and beat/chord events in the shared exclusive-observed and half-open interval convention. A mismatch or invalidated run is an explicit stale result, not a successful empty timeline. The UI must clear old details before accepting a different identity, and display uncalibrated scores as strengths rather than percentages. Neither interface implies querying SQLite or analyzing files on the GUI thread. The library owner and integration owner must review pagination consistency, identity and lifetime before implementation; the current `AnalysisStore::find` is a cache operation and cannot enumerate the collection.
