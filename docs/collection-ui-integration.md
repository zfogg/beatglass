# SQLite collection UI integration proposal

The filesystem browser is a view of a directory, not an indexed collection. The accepted AnalysisStore contract supplies typed cache lookup and publication outcomes, but does not expose a collection query; the library backend prototype does not yet supply completed result serialization. Before connecting a collection table, the integration owner and library backend should agree on a worker-owned query API returning immutable, bounded pages with stable track identity, path/availability, metadata, analysis status and typed error/cancellation outcomes. Filter and sort requests need explicit ordering, request generations and cancellation or stale-response rejection; SQLite work stays off the GUI thread. Results should identify the source file version and analysis configuration so selecting a row cannot silently display a prior file version's result. A missing or moved file remains a visible entry with a recoverable status, and removing an entry must not delete the source.

A selected result needs its own immutable detail value with sample rate, epoch or file identity, exclusive observed frame boundary, nonempty half-open chord segments, beat positions and explicit unknown values. Playback position is in milliseconds from Qt Multimedia; convert carefully to sample frames using the result's sample rate, clamp only for display, and clear the detail view when the selected file/version changes. The player and analysis decoder may support different formats and must report their own errors. Playback/seek must remain optional and must not be used as evidence that the analysis or cached result exists. A worker-to-GUI delivery contract must define ordering, bounded updates, shutdown, and session identity across reconnects. User audio and tags remain read-only.

The current backend prototype does not meet these requirements and no UI call depends on this proposal. End-to-end tests should cover real indexing, unchanged-file reuse across restart, modified/missing files, stale asynchronous responses, result identity, cancellation, and seeking across half-open timeline boundaries. Native audio and GUI qualification remains separate.

## Proposed first query and detail handoff (not yet accepted)

The UI needs a worker request keyed by a session and monotonically increasing request ID, with search text, an explicitly selected sort field/direction, and a bounded page cursor. A successful page contains stable track IDs, display title/artist or explicit absence, path, availability, optional duration, optional BPM/key, and analysis state. Miss/empty, cancellation and error remain distinct. A cursor must either hold a consistent query snapshot or report invalidation; the UI discards results for older request IDs and clears selection if its track/version is removed or replaced.

A detail request takes the stable track ID and the active run ID or version token returned by the page. Its response includes that identity, sample rate, track duration, status, optional BPM/key candidates, and beat/chord events in the shared exclusive-observed and half-open interval convention. A mismatch or invalidated run is an explicit stale result, not a successful empty timeline. The UI must clear old details before accepting a different identity, and display uncalibrated scores as strengths rather than percentages. Neither interface implies querying SQLite or analyzing files on the GUI thread. The library owner and integration owner must review pagination consistency, identity and lifetime before implementation; the current `AnalysisStore::find` is a cache operation and cannot enumerate the collection.

## Review notes for the #54 prototype

The draft worker-owned `SqliteCache::entries` returns bounded owned pages, supports literal search and whitelisted path/title/artist order, and distinguishes cooperative cancellation from storage exceptions. Its offsets can shift when rows change, its matching and sort semantics are ASCII-only, and its entry path and modification-time representations remain provisional. These are useful initial primitives but are not yet the identity-bound collection contract above. Before a product Qt model depends on them, the library and integration owners should decide how the UI detects a shifted page or refreshes a changing collection; define UTF-8 path normalization and timestamp semantics across platforms; and provide stable entry/run identity, active-analysis status, and an exact selected-result detail operation that cannot attach a cached result to a replaced file. A nonempty content hash in `CollectionEntry` is caller-supplied evidence, not validation of the current path.

The draft `analyze_snapshot_to_store` is a synchronous worker-owned tempo-only operation with a stop token, frame progress and typed result; it currently returns no beat/chord history. A UI-facing job boundary still needs a bounded queue, a per-job cancellation handle, generation-tagged progress and terminal outcomes delivered to the GUI thread, a defined shutdown policy, and a durable mapping from the indexed entry to the committed run. Progress should be throttled or coalesced while terminal errors and clears remain observable. Until the snapshot-verification and verification-to-commit races, accepted decoder/replay, and schema coordination are closed, this private prototype must not be presented as a validated product result. These notes are a review proposal, not an accepted contract or a claim that the row status exists today.

## Proposed worker adapter for #56

The #56 private `TempoAnalysisStore` owns the SQLite connection exclusively and exposes bounded metadata `entries` and exact-path `entry`; `analyze_snapshot_to_store` returns an owned tempo-only `StoredSnapshotJobResult` and takes a stop token, epoch, and synchronous progress callback. Its job executor offers bounded submission and a cancellable `JobHandle`, but the handle carries only coarse state and frames; it does not retain the typed `StoredSnapshotJobResult`. The exact-path detail query returns metadata only, not a validated active run/result. The Qt layer therefore must not infer a committed result from a row's caller-supplied content hash or from `JobHandle::completed`.

Propose one long-lived library worker that constructs, uses and destroys the store on that worker, and serializes collection queries and snapshot jobs through a bounded queue. Each request carries a process-session ID and monotonically increasing request ID; start returns either a cancellable handle or a typed queue-full/stopping error. Query responses own their page and distinguish completed empty, cancelled and error. The worker coalesces frame progress per live job, but retains one typed terminal result (cache hit, committed, cancelled, stale input, error/indeterminate with recovery run ID) until the GUI acknowledges or shutdown drains it. Qt objects are created/updated only on the GUI thread. Selection changes invalidate outstanding detail requests; results are accepted only for the same selected entry and verified source/run identity. Shutdown stops acceptance, requests cancellation, resolves or reports commit-in-progress outcomes, closes the database on its owner thread, then joins; a destroyed GUI/session cannot receive a late result.

For the first real vertical slice, the library owner should expose an owned operation that atomically associates an indexed path/version with a validated active analysis identity and retrieves its tempo-only result or an explicit missing/stale/error outcome. The current `entry(path)` plus `find(FileVersion, AnalysisIdentity)` cannot safely make that association from an unverified row hash, and publication versus metadata updates need an explicit transaction/consistency decision. Full track search, progress status across restart, and future chord/beat results should build on that identity rather than assume offset pages or path strings are stable IDs. These are proposed review questions for #54/#56, not an approved API; no UI code depends on them yet.

## Composite result semantics for DSP and library review (#55/#56)

The proposed composite callbacks report causal beat events and overlapping tonal-analysis windows, not a track-level key or a chord-segment timeline. A UI DTO should retain each window's epoch, sample rate, half-open chord-analysis bounds, separate optional key evidence start, optional labels and uncalibrated strengths. Display key as a rolling/local estimate with its evidence range; the final window must not be relabeled as a validated whole-track key. Windows may overlap and should be rendered as observations or summarized only by a separately specified segmentation policy. Do not concatenate them into non-overlapping chord segments or infer boundaries from callback cadence.

`CausalMusicBeat` supplies a frame, exclusive observation boundary, epoch and sample rate, but no beat strength. The existing shared `Beat::strength` is a required float; propose either an optional strength or an explicit availability flag in the owned offline DTO and shared snapshot schema before persisting or displaying this information. Zero must not stand in for an unknown measured strength. Event order, valid epoch/observed boundaries, bounded event counts, schema and algorithm versions, stale/clear handling, and overflow behavior need integration-owner approval. The existing #56 tempo-store serializer explicitly rejects beat, chord and candidate collections; adding the composite output requires a new versioned result format and transactional association to the validated active source/run, not silent truncation or an overwrite of the tempo-only blob. This is a proposed contract and visualization policy, not a product result or an accuracy claim.

## Review of the new #56 LibraryBridge

The new `LibraryBridge` owns its store on a dedicated worker, transfers owned results through an injected dispatcher and suppresses stale or post-destruction callbacks. That is a useful base, but its single latest-request lane cancels any active operation when a page or detail request arrives; using it directly for the requested collection UI would let ordinary browsing cancel analysis. Its suppressed completion may already have committed, dispatcher exceptions drop completion, and the bridge does not expose `put_entry`, analysis progress, a retained typed terminal result, or an identity-bound active-result lookup. Its incrementing request generation also needs an explicit exhaustion policy. The current exact-path detail returns metadata rather than a validated active analysis. These constraints should be resolved with the library owner before wiring a product flow.

Concrete proposal: keep one database owner, but separate coalescible page/detail requests from durable analysis jobs; use bounded, explicitly rejected submissions and per-job cancellation. The worker may serialize both kinds of operation, but a newer page request must not cancel a job. Retain terminal job outcomes and run IDs until acknowledged, including an indeterminate commit that requires recovery; make dispatcher failure observable or recoverable by polling. Use a session identity plus non-wrapping request revisions for stale GUI callbacks, an owned progress snapshot, and a GUI-lifetime-safe queued dispatcher. Add an atomic identity-checked association/read operation for a selected indexed path and active completed run. Only after the source verification/commit contract and these operations are accepted should the GUI enable analyze/status/details against this prototype. No database access, hashing, decoding or DSP runs on the GUI thread.

### Library review update at #56 `6d1b2f7`

The bridge now returns a shared ticket whose owned typed terminal result can be polled even after bridge destruction or dispatch failure. A new lookup accepts a caller-supplied content/engine/configuration/mode identity, opens and revalidates a fresh snapshot, and distinguishes hit, miss, changed, cancelled and error; on a hit it rebinds cached positions to the caller's nonzero session epoch. This improves recovery and stale-input detection, but it does not discover a validated active identity for a selected indexed entry: a row's caller-supplied hash is still insufficient. The snapshot modification/restoration and verification-to-commit races remain open, so a hit is provisional rather than a product-verified result. The bridge still has one global latest-request lane, increments a wrapping generation, can suppress callbacks after a commit, and may block during shutdown. Pollable tickets do not make analysis submissions independent of browsing or define acknowledgement and commit recovery. No GUI integration should infer a safe active result from this lookup alone.

For #57 `7c107df`, retain owned optional beat strengths as unknown when absent, preserve overlapping tonal windows and each rolling key's independent evidence range, and keep optional validated track key separate from rolling/local key evidence. Its validator checks structure only; it supplies neither persistence nor identity-verified paging. A future GUI adapter must carry those distinctions through GUI-thread delivery and selection/revision changes without synthesizing missing values. End-to-end acceptance remains blocked until the library and integration owners agree on identity-bound paged retrieval, job lifetime and source verification, then test indexing, analysis, restart/reuse, source replacement, cancellation, stale delivery and shutdown through the actual desktop.

### Library review update at #56 `528848c`

The worker now has separate browse and analysis cancellation lanes and offers `analyze_indexed` and `lookup_indexed`. It reports an index-association failure separately from a committed analysis, and indexed lookup re-snapshots the path before a tempo-only lookup. This supersedes the single-lane and absent-lookup observations above. Association is a separate update after publication rather than an atomic active-run binding, and the filesystem verification-to-commit race remains open. Browse and lookup share a lane; a long analysis can delay both on the one worker. A GUI integration must retain the analysis ticket after cancellation, expose association failures, marshal owned callbacks to a lifetime-bound GUI context, and keep result display gated until the source and association guarantees are accepted. The branch remains unconnected to this desktop; no end-to-end desktop claim follows from the library's tests.

### Process epoch handoff proposed for integration review

One process-scoped control owner must retain the existing non-thread-safe `SourceEpochAllocator` for the entire process session. GUI-originated offline requests and live-worker start or reacquisition requests are serialized through that owner; it issues a fresh nonzero value and transfers the value to the requesting worker. No callback allocates an epoch, and the allocator itself is never accessed concurrently or recreated with an individual window, capture or job. Exhaustion rejects the request and clears affected presentation without wrapping. A stopped or superseded request discards a late grant by request identity; shutdown stops accepting requests and drains or invalidates pending grants before the owner is destroyed. A separate process session must not accept old queued deliveries.

Today `WindowsDj::run` constructs its own worker-local allocator and `CollectionView` accepts externally supplied epochs. They are not a shared process coordinator. The Windows and integration owners must agree on a bounded request/response handoff and teardown ordering before changing the live platform contract or wiring collection actions. Tests must interleave offline jobs with selected/default live start and reacquisition, cancellation, stale grants, recreation and exhaustion; callbacks remain copy-only. Until then no product action may supply a UI-local counter or constant as an epoch. Runtime dependency/configuration identity is similarly required before cache reuse or result display; #60 explicitly returns uncached evidence with unverified dependency identity.

An alternative now proposed by the coordinator is a single process-owned allocator whose `next()` uses atomic compare-and-swap and can be called concurrently by non-callback GUI/control/library workers. This replaces the serialized handoff proposal above if the shared contract is approved. Inject the same instance into `WindowsDj`, each live selected/default follower, and every offline job; create it before all consumers and destroy it only after workers join and queued consumers are invalidated. Never call it from capture callbacks. Exhaustion returns no value without wrapping and all affected paths fail closed. Request generations must still reject stale grants and results; thread safety alone does not identify a process session, so restart needs a distinct session identity or a proven drain. Review and tests should cover concurrent uniqueness, exhaustion at the boundary, window and worker recreation, interleaved live reacquisition and offline jobs, cancellation, stale callbacks and shutdown. Do not silently change the existing non-thread-safe header contract before integration-owner review.

The UI draft now stacks the coordinator's proposed #63 and implements the injection for its two current consumers: `main` owns one allocator, passes it by reference to `WindowsDj` and the optional `CollectionView`, and destroys both before it. Windows selected/default live sources borrow that same instance on their worker; collection analysis and initial lookups allocate on the GUI thread. A continued offline page requires the previous page's run and source and reuses that page session's epoch. Missing identities and exhausted allocation fail closed; new collection operations never use `FileReader`'s local seek increment. The process-session identity/drain contract, Windows-owner review, additional platforms, real composite worker and runtime identity remain open. The internal collection APIs are not exposed as product analysis controls.

### Bounded archive integration update

The draft UI branch consumes the library archive and its `65885ed` retention fix for review: a page is run-scoped, independently bounded and revalidated against a fresh source snapshot; a superseded run returns changed. The returned header releases full decoded event-vector capacity, though each page still temporarily decodes an archive capped at 8 MiB. The internal Qt adapter clears old pages on selection/request changes and never presents them as verified product results. Atomic index publication improves the earlier separate-update prototype; source races, runtime identity and native qualification remain open.
