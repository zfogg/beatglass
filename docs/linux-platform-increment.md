# Linux platform work: initial discovery increment

The experimental PipeWire registry discovery in `lib/capture/pipewire/discovery.cpp` collects `Audio/Sink` nodes with both a node name and object serial. A sync barrier bounds the initial registry snapshot; removal events before the barrier remove the corresponding entry. Failure or timeout returns an error rather than a successful empty list. Serial identifies an object only for the lifetime of the PipeWire server; a persisted user preference needs a separate reidentification policy. Enumeration is a snapshot: a sink can disappear before start. This implementation is private and is not wired into the application.

The integration owner should approve a shared source API that distinguishes successful empty enumeration, cancellation and backend failure, carries object serial and descriptive identity without promising cross-server stability, and reports device loss after selection. Capture requires a process-wide epoch owner, bounded audio delivery, valid/absent clock anchors, explicit format changes, ordered failure notifications and stop quiescence as described in `phase1-contract-proposals.md`. A session-managed capture may request `target.object` with `stream.capture.sink=true`; the experiment below instead creates explicit links. Discovery alone does not capture audio. See [PipeWire streams](https://docs.pipewire.org/page_streams.html) and [sink monitor example](https://docs.pipewire.org/page_module_loopback.html). Do not silently fall back to a microphone or a different sink.

No Linux overlay implementation is present. X11 window-manager stacking and input-shape behavior must be tested with a real window manager; Wayland compositors can restrict positioning, stacking and input behavior. Layer-shell support and KDE, GNOME and other compositor behavior require runtime probing and native tests. A normal control window and an explicitly described non-overlay fallback are required where those capabilities are unavailable; no universal always-on-top or click-through guarantee is made.

Development verification on 2026-11-07: Windows host, Ubuntu 22.04 WSL2, GCC 11.4, PipeWire development package 0.3.48. `cmake -S . -B /tmp/beatglass-foundation-linux -G Ninja -DBUILD_TESTING=ON -DBEATGLASS_BUILD_PIPEWIRE=ON`, `cmake --build /tmp/beatglass-foundation-linux -j 4`, and `ctest --test-dir /tmp/beatglass-foundation-linux --output-on-failure`: all 25 registered tests passed, including registry filtering, removal and an unreachable-daemon error. These tests do not connect to a real daemon, exercise capture, or qualify native Linux, X11, Wayland, audio, or overlay behavior. The optional root build target and Linux CI job compile the production discovery library; the internal header is provisional and is not installed.


## Experimental monitor prototype (not integrated)

The private monitor disables session-manager autoconnection and creates two explicit links from the selected sink's monitor ports to the capture stream after an initial registry sync. It asks PipeWire to convert to interleaved 48 kHz stereo float and copies validated chunks into a bounded SPSC queue. Whole-block overflow advances frame positions and marks the next accepted block discontinuous. Invalid or corrupted input ends the epoch; pause/error requires a new instance and epoch. A bounded SPSC control-event queue reports ordered attempt/sequence transitions; observed graph loss, malformed data, metadata discontinuity and queue overflow invalidate capture. After the control owner consumes and applies the running event and resets analysis, the worker must install the exact epoch and fixed format before any block can be popped; an interruption revokes that installation. The source checks both channel links from monitor ports on the selected sink and completes a registry sync before accepting PCM. Its zero block timestamp is an unavailable anchor, not a measured time. PipeWire graph-clock snapshots are measured and exposed separately; they are not sample-position anchors. It must not be connected to product analysis until event delivery, the worker barrier and clock handoff are integrated and ordering between graph changes and queued audio is resolved. Other clients can still add links to the stream, so observed graph updates are not yet a proven boundary against wrong-source PCM.

An isolated Ubuntu 22.04 WSL2 graph with PipeWire 0.3.48 and WirePlumber 0.4.8 now captures a generated stereo tone from a selected non-default virtual sink. The opt-in `BEATGLASS_TEST_PIPEWIRE_GRAPH=ON` test creates two driven null sinks, sends the tone to the selected sink, checks the captured frame metadata and repeated signal crossings, and rejects a sink absent at preflight while a different sink plays. Three consecutive earlier graph runs passed, followed by a run with the stronger signal check. Test setup uses an isolated D-Bus session and disables the Bluetooth monitor because WSL lacks logind. PipeWire media-session was not requalified after this correction. The adapter uses server-session serial and name during discovery and endpoint verification, and links graph port IDs explicitly. Disabling autoconnection avoids relying on session-manager fallback policy, but object IDs may be removed or reused between discovery and link creation. The adapter now checks the observed actual links and fails closed on observed loss. Registry notifications and audio graph cycles are asynchronous, so this does not yet prove that no stale or wrong-source block can be accepted during a link change; that ordering and revocation race remains unresolved before product use. Real Linux hardware, device loss, permission denial, session manager variants, actual desktop X11/Wayland and overlay qualification remain untested. The graph test requires `pipewire`, `wireplumber`, `dbus-run-session`, `pw-play`, `pw-dump`, `wpctl`, and Python.

The source contract merged in PR #28 provides typed results, attempt and lifecycle types, and optional clock anchors. The monitor returns typed start/enumeration results and emits events using those types, but integration still needs a concrete event transport that conveys ordered attempt/sequence transitions and delivery loss, integration of the private worker barrier installing format/epoch before PCM, and a way to associate an optional clock anchor with blocks. `AudioBlock::monotonic_ns` remains mandatory and cannot by itself express an unavailable anchor. Start/enumeration cancellation and selected sink serial identity across server restarts also need explicit integration semantics. The monitor prototype deliberately does not claim full conformance to the merged contract.

A virtual-graph scenario also destroys the selected sink after receiving PCM, applies the ordered interruption or error event, recreates a sink with the same name and a different serial, and verifies that the old attempt and worker gate remain invalid. Five consecutive WSL runs passed. The test feeds captured blocks through shared continuity and tracking helpers and verifies that clearing the snapshot publisher rejects a stale token and that the presentation gate rejects a delayed update after a revisioned clear. With the optional file-analysis dependencies enabled, an additional virtual-graph test feeds captured generated pulses through the shared channel reducer and aubio tempo tracker, requires a tempo estimate and checks reset on discontinuity. This is test-only integration and does not enable the product DSP or UI. This is not native-device qualification.

## DSP and UI handoff questions

The analysis owner must apply the running event to its retained `SourceLifecycle`, reset estimators and publication, install the given epoch/format on the worker, and only then pop blocks. Any interruption, error, delivery loss, queue overflow or discontinuity must revoke the worker gate, invalidate in-flight tracking tokens and send the UI a revisioned clear. The UI cannot treat a previously displayed snapshot as current merely because a new block has arrived. No product connection is enabled by this private prototype.

`pw_stream_get_time` is RT-safe and reports a graph-driver clock snapshot, including ticks, rate and delay; it does not by itself identify the time of the first sample in a dequeued block. PipeWire 0.3.48 also predates the resampler-buffered timing field. A valid `AudioClockAnchor` needs a documented mapping from the buffer and converter/queue state to its frame position, a clock domain, and known limitations or uncertainty; a graph timestamp or callback arrival time must not be substituted. See [PipeWire stream timing](https://docs.pipewire.org/structpw__time.html) and [buffer header metadata](https://docs.pipewire.org/structspa__meta__header.html).

Registry events and data callbacks need an ordering mechanism that proves no block accepted after graph rerouting can retain the former source identity. A registry sync proves an observed control snapshot only; it is not a documented barrier for already scheduled graph processing or worker-held blocks. Until the adapter can establish that boundary and revoke stale publications, fail closed and keep the product path disconnected.

The monitor translation unit also compiled with `-std=c++20 -Wall -Wextra -Werror` against Ubuntu 24.04 PipeWire 1.0.5 development headers in a Docker container. This checks API compatibility only; that container run did not exercise a graph or hardware.

The experimental monitor now disables autoconnection and creates two links through PipeWire's [link factory](https://docs.pipewire.org/page_module_link_factory.html). An isolated graph test injects a second sink's monitor into the stream; observed wrong links invalidate the attempt, and ten consecutive runs detected no wrong-channel PCM escaping before invalidation. A later `ctest --test-dir /tmp/beatglass-foundation-linux -R pipewire_wrong_link --repeat until-fail:30 --output-on-failure` run also passed all 30 iterations. These tests do not prove the absence of that race: registry notifications can lag graph processing, and PipeWire versions before 1.6 do not provide the documented `port.exclusive` property that restricts a port to one link. Factory inputs use graph object IDs that may be removed or reused; explicit links and registry sync alone do not prove when worker-held blocks and published results cease to be valid. Tests of replacement between discovery and link creation, user-visible revocation of already displayed results, and native session-manager behavior remain required.

The optional captured-tempo scenario uses a generated 120 BPM pulse train routed through the selected virtual output sink, the monitor queue and the shared aubio tracker. It is a smoke test of real code and captured PCM, not a quality or latency qualification for music, and does not validate key, chords, an overlay or a sample clock. Local WSL verification on 2026-11-07 used `cmake -S . -B /tmp/beatglass-foundation-linux -G Ninja -DBUILD_TESTING=ON -DBEATGLASS_BUILD_PIPEWIRE=ON -DBEATGLASS_TEST_PIPEWIRE_GRAPH=ON -DBEATGLASS_BUILD_SLICE=ON -DBEATGLASS_TEST_V1_CODECS=OFF`, `cmake --build /tmp/beatglass-foundation-linux -j 1`, and `ctest --test-dir /tmp/beatglass-foundation-linux --output-on-failure`: all 53 tests passed, including captured tempo; after merging the CLI JSON work (#25), the same serial build and full CTest run passed 54 tests. A subsequent verbose run after tightening the accepted range to 110–130 BPM reported 121.305 BPM for the generated 120 BPM pulses. Reconfiguring with `-DBEATGLASS_BUILD_SLICE=OFF`, rebuilding with `-j 1`, and running `ctest --test-dir /tmp/beatglass-foundation-linux -L pipewire --output-on-failure` passed all 15 PipeWire tests without the optional DSP dependency. The older WSL libsndfile configuration omits codec qualification.

## Shared DJ UI and Linux overlay handoff

The normal DJ control page must remain usable when no overlay capability is verified. It should identify the selected output sink, distinguish starting/running/interrupted/error and delivery loss, and explain that only that sink's combined output is monitored. On stop, source loss, overflow, discontinuity or error, the analysis owner invalidates the acquisition token and queues a revisioned clear to the GUI; the GUI applies the newest revision on its own thread and clears BPM, beat phase, key and chord values. A prior rendered value is stale until the clear arrives, and a delayed older snapshot must not restore it. A current anchor is optional: without a defensible sample-clock mapping, do not schedule a beat pulse from a fabricated zero timestamp. The existing QML page remains a navigation shell, not an implemented monitor or overlay.

Probe the running window system and actual compositor capabilities; do not infer support from a desktop name or from a Qt flag alone. Under X11, inspect the window manager's `_NET_SUPPORTED` hints and input-shape support, request stacking only where available, and treat the result as subject to window-manager policy. Under Wayland, probe whether the compositor advertises layer-shell and whether an adapter can actually create and configure an appropriate surface; support for that protocol is not a promise that arbitrary positioning, fullscreen stacking or click-through will work. GNOME, KDE and other compositors require separate native observation; absence, refusal or loss of the required capability falls back to an ordinary compact window. The fallback must not claim fullscreen-overlay behavior. See the [X11 EWMH specification](https://specifications.freedesktop.org/wm/latest/ar01s03.html), [Qt's Wayland positioning notes](https://doc.qt.io/qt-6/application-windows.html), and the [layer-shell protocol](https://raw.githubusercontent.com/swaywm/wlr-protocols/master/unstable/wlr-layer-shell-unstable-v1.xml).

Click-through may only be offered when the selected backend can both establish it and retain an independent, discoverable control-window path to unlock or hide the overlay. Do not rely solely on a global shortcut: its availability and portal permission are separate capabilities. On display removal, scaling changes, compositor restart or layer-surface closure, revalidate the selected output and geometry, revoke stale overlay assumptions, and return to an interactive compact window if recovery is unavailable. Persist only validated settings and restore to an accessible screen.

Qualification requires actual Linux desktop sessions on X11 and multiple Wayland compositors, including KDE and GNOME, with build identity, compositor/session version, output routing, fullscreen application, monitor/DPI changes, input pass-through and recovery evidence. WSL, a virtual PipeWire graph and headless tests do not qualify these scenarios. Capture permissions and portal behavior also need checking in the actual package. None of these probes, overlay behaviors or native scenarios is implemented or qualified by this PR.

## Clock and graph isolation investigation

PipeWire 1.0.5 and newer document `pw_buffer::time` as the graph-cycle time when a capture buffer was queued. It is not documented as the time of that buffer's first audio frame. `pw_time` reports graph-clock position and delay, and newer versions include converter buffering, but the present adapter does not establish a frame-accurate relationship across the converter, queue and graph clock. Thus the safe fallback remains an absent `AudioClockAnchor`; the observed graph clock is diagnostic only. Establishing an anchor requires version-specific evidence about the buffer's first-frame mapping, clock domain, buffering, drift and uncertainty, plus actual-device validation. See [PipeWire buffer timing](https://docs.pipewire.org/structpw__buffer.html) and [stream timing](https://docs.pipewire.org/structpw__time.html).

PipeWire documents `port.exclusive` as enforced from 1.6, restricting a port to one link; the tested 0.3.48 and compiled 1.0.5 environments do not provide that documented guarantee. `node.exclusive` requests exclusive resource access and must not be substituted without proving that ordinary playback is unaffected. A future experiment could use input ports with verified server-enforced exclusivity, but must demonstrate that the capture adapter can set the property on its actual ports, that an additional link is refused by the server, that target replacement cannot bind the wrong object, and that in-flight worker and GUI publications are revoked. No such exclusive-port path is implemented or claimed here. See [PipeWire key documentation](https://docs.pipewire.org/group__pw__keys.html) and [upstream release notes](https://github.com/PipeWire/pipewire/blob/master/NEWS).

On 2026-11-07 after the last capture-test change, the combined WSL configuration was rebuilt serially and `ctest --test-dir /tmp/beatglass-foundation-linux --output-on-failure` passed all 54 tests, including the tightened 110–130 BPM captured-tempo assertion. This still excludes the optional Qt desktop and v1 codec qualification.
