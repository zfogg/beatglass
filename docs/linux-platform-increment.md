# Linux platform work: initial discovery increment

The experimental PipeWire registry discovery in `lib/capture/pipewire/discovery.cpp` collects `Audio/Sink` nodes with both a node name and object serial. A sync barrier bounds the initial registry snapshot; removal events before the barrier remove the corresponding entry. Failure or timeout returns an error rather than a successful empty list. Serial identifies an object only for the lifetime of the PipeWire server; a persisted user preference needs a separate reidentification policy. Enumeration is a snapshot: a sink can disappear before start. This implementation is private and is not wired into the application.

The integration owner should approve a shared source API that distinguishes successful empty enumeration, cancellation and backend failure, carries object serial and descriptive identity without promising cross-server stability, and reports device loss after selection. Capture requires a process-wide epoch owner, bounded audio delivery, valid/absent clock anchors, explicit format changes, ordered failure notifications and stop quiescence as described in `phase1-contract-proposals.md`. The selected serial should be passed as `target.object` with `stream.capture.sink=true`; discovery alone does not capture audio. See [PipeWire streams](https://docs.pipewire.org/page_streams.html) and [sink monitor example](https://docs.pipewire.org/page_module_loopback.html). Do not silently fall back to a microphone or a different sink.

No Linux overlay implementation is present. X11 window-manager stacking and input-shape behavior must be tested with a real window manager; Wayland compositors can restrict positioning, stacking and input behavior. Layer-shell support and KDE, GNOME and other compositor behavior require runtime probing and native tests. A normal control window and an explicitly described non-overlay fallback are required where those capabilities are unavailable; no universal always-on-top or click-through guarantee is made.

Development verification on 2026-11-07: Windows host, Ubuntu 22.04 WSL2, GCC 11.4, PipeWire development package 0.3.48. `cmake -S . -B /tmp/beatglass-foundation-linux -G Ninja -DBUILD_TESTING=ON -DBEATGLASS_BUILD_PIPEWIRE=ON`, `cmake --build /tmp/beatglass-foundation-linux -j 4`, and `ctest --test-dir /tmp/beatglass-foundation-linux --output-on-failure`: all 25 registered tests passed, including registry filtering, removal and an unreachable-daemon error. These tests do not connect to a real daemon, exercise capture, or qualify native Linux, X11, Wayland, audio, or overlay behavior. The optional root build target and Linux CI job compile the production discovery library; the internal header is provisional and is not installed.


## Experimental monitor prototype (not integrated)

The private monitor requests an explicitly selected object serial with `stream.capture.sink=true` and disables automatic reconnect. It asks PipeWire to convert to interleaved 48 kHz stereo float and copies validated chunks into a bounded SPSC queue. Whole-block overflow advances frame positions and marks the next accepted block discontinuous. Invalid or corrupted input ends the epoch; pause/error requires a new instance and epoch. A bounded SPSC control-event queue reports ordered attempt/sequence transitions; observed graph loss, malformed data, metadata discontinuity and queue overflow invalidate capture. The source checks both channel links from monitor ports on the selected sink and completes a registry sync before accepting PCM. Its zero timestamp is an unavailable anchor, not a measured time. It must not be connected to product analysis until event delivery, the worker epoch/format barrier, clock handoff and ordering between graph changes and queued audio are integrated. Session manager policy can reject or fail to honor target selection; there is no verified defense yet against fallback to a different endpoint.

An isolated Ubuntu 22.04 WSL2 graph with PipeWire 0.3.48 and WirePlumber 0.4.8 now captures a generated stereo tone from a selected non-default virtual sink. The opt-in `BEATGLASS_TEST_PIPEWIRE_GRAPH=ON` test creates two driven null sinks, sends the tone to the selected sink, checks the captured frame metadata and repeated signal crossings, and rejects a sink absent at preflight while a different sink plays. Three consecutive earlier graph runs passed, followed by a run with the stronger signal check. Test setup uses an isolated D-Bus session and disables the Bluetooth monitor because WSL lacks logind. PipeWire media-session was not requalified after this correction. The adapter supplies both `target.object` (serial) and the older `node.target` (name) because the tested older session manager ignored the former; uniqueness is checked at preflight. Target disappearance, replacement or rename after that check can still lead to fallback on a manager that ignores `node.dont-fallback`. The adapter now checks the observed actual links and fails closed on observed loss. Registry notifications and audio graph cycles are asynchronous, so this does not yet prove that no stale or wrong-source block can be accepted during a link change; that ordering and revocation race remains unresolved before product use. Real Linux hardware, device loss, permission denial, session manager variants, actual desktop X11/Wayland and overlay qualification remain untested. The graph test requires `pipewire`, `wireplumber`, `dbus-run-session`, `pw-play`, `pw-dump`, `wpctl`, and Python.

The draft source contract in PR #28 is a useful lifecycle basis, but PipeWire integration still needs a concrete event transport that conveys ordered attempt/sequence transitions and delivery loss, an explicit worker barrier installing format/epoch before PCM, and a way to associate an optional clock anchor with blocks. `AudioBlock::monotonic_ns` remains mandatory and cannot by itself express an unavailable anchor. Start/enumeration cancellation and selected sink serial identity across server restarts also need explicit integration semantics. The monitor prototype deliberately does not claim conformance to that draft contract.

A virtual-graph scenario also destroys the selected sink after receiving PCM and verifies an ordered running event followed by an interruption or error event, with no subsequent block accepted. Three consecutive WSL runs passed. This is not native-device qualification.
