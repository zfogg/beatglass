# Composite dependency identity: verification proposal

This is an integration proposal, not an implemented verifier. Composite cache lookup and publication stay disabled. The `UnverifiedMusicAnalysis` flag is always false; a structurally valid `OfflineAnalysis` or nonempty strings are not proof of provenance.

## What must be identified

Cache identity must cover the exact Beatglass analysis implementation, aubio tempo/beat implementation and FFT backend, Essentia implementation and FFT backend, decoder and relevant transitive libraries, target architecture/ABI and effective build options, as well as the actual mode, input sample format/rate, downmix rule, silence thresholds, tempo windows/hops, Essentia algorithm parameters and defaults, and key/chord profiles/windows/history. A canonical representation must be generated from the same values actually used by the implementations; a caller-provided label or selected constants alone cannot establish completeness. Defaults embedded in dependencies and runtime-selected backends must also be identified. Source content identity, publication and process-session epochs remain separate checks.

A proposed build manifest should enumerate exact artifacts and dependencies, complete effective configuration, an implementation/schema version, and a cryptographic digest for each artifact. It should be generated from the locked build and authenticated by a trusted release authority. The hashes emitted by the experimental #70 recipe are only candidate build output: they are not signed, do not enumerate all transitive dependencies, and are not compared with the code actually mapped at runtime. Any missing, unsupported, mismatched or changed evidence must produce no cache lookup or publication. Do not turn a caller-supplied manifest into a `verified` boolean.

## Windows candidate

Package a tightly controlled analysis worker and its complete non-system dependency closure in a versioned, access-controlled installation. Record and authenticate artifact hashes and complete configuration in the release manifest. At startup establish a reviewed process and code-integrity policy, identify the actual executable and loaded module images, and bind each measured artifact to the corresponding mapped image without a pathname replacement race; monitor or prohibit later unapproved module loads for the full analysis lifetime. Bind platform-provided dependencies to an identified OS/build or include their actual verified identities. Distinguish statically linked code, which belongs to its containing image, from dynamically loaded DLLs and FFT backends. A path returned by [`GetModuleFileName`](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulefilenamew), or the existing address-to-path observer, is useful for discovery but does not itself prove the mapped bytes. A signature check on a reopened path is also insufficient without a race-resistant binding to the loaded image. The [Windows binary-signature mitigation](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-process_mitigation_binary_signature_policy) offers Microsoft/Store signing restrictions; it is not a general custom Beatglass artifact allowlist. Establishing such a policy, protecting it from overrides, and proving the file-to-image binding remain unsolved for the current packaging.

## macOS candidate

Use a signed, notarized worker with [Hardened Runtime and library validation](https://developer.apple.com/documentation/security/hardened-runtime), without exceptions that permit arbitrary libraries or dynamic-loader injection. Verify the actual worker and each relevant mapped image against authenticated exact-build identities, not merely a permissive signer or designated requirement. Include system libraries or an OS/build identity and detect or prohibit changes in the loaded dependency set during the analysis. Apple's [code requirement guidance](https://developer.apple.com/documentation/security/applying-code-requirements) provides a way to evaluate a chosen identity policy; a designated requirement can intentionally accept updates and is therefore not by itself a cache version. A `dladdr` pathname and a static signature check on whatever file currently occupies that path do not bind it to mapped bytes. The signed packaging, exact-image binding, dependency closure and loader-change policy are not implemented or qualified.

## Required tests before enabling reuse

Use packaged native Windows and macOS builds with known test identities. Check exact matches, changed analysis parameters and defaults, replaced or modified direct and transitive libraries, wrong signer/build/architecture, path and symlink replacement, module load/unload during analysis, unsupported platform evidence, failure or cancellation at each boundary, and distinct OS dependency identities. Each uncertainty must prevent both lookup and publication. Exercise actual source revalidation and atomic store publication separately. Verify dynamic loading, code-signing and threat-model assumptions with the platform owner; desktop UI or headless CI alone is not native audio qualification.
