# Experimental Essentia tonal tracker

This opt-in worker path runs actual Essentia spectral and key algorithms on observed mono PCM. When `BEATGLASS_BUILD_MUSIC_REPLAY=ON` is enabled, the combined CLI connects it to Library replay and the Live worker; the normal build still reports tonal analysis as unavailable. It is not used by storage identity unless the corresponding experimental analysis configuration is enabled. It uses 4096-sample Hann windows and 2048-sample hops, a bounded 32-frame HPCP history for the key, and the most recent HPCP for a local major/minor triad. It uses no samples after the reported exclusive frame boundary. Strengths are raw algorithm correlations, not calibrated probabilities. Silence, gaps and epoch changes clear history; a new label after a gap requires a complete window. The latest result is a window-level estimate, not a chord segment, and no transition timing or full-mix accuracy is claimed.

`BEATGLASS_BUILD_TONAL_SPIKE=ON` requires a compatible Essentia C++ library and Eigen3; default builds do not enable it. Essentia must have Windowing, Spectrum, SpectralPeaks, HPCP and Key algorithms registered, and its factory creation must be serialized until concurrent construction has been qualified. The process retains Essentia's global initialization until exit. Audio capture callbacks may not instantiate or call this tracker. Build and licensing research is tracked separately in the Essentia dependency spike PR; the option is not a distribution decision. No substitute estimator is used if Essentia is missing.

The library cache proposal to decode from a private immutable snapshot can be supported through libsndfile virtual I/O, but the current FileReader does not provide that adapter. A borrowed, seekable byte source must remain alive until `sf_close` returns and must not be accessed concurrently with decoder calls unless explicitly synchronized. The adapter needs checked 64-bit length, tell and seek operations, bounded reads, a distinction between EOF, error and cancellation outside libsndfile's C callbacks, and no C++ exception may escape those callbacks. A cancellation request must be checked during snapshot creation and between decoder calls; its latency during a blocking read is bounded only by the byte source. Snapshot creation must be exclusive, private and complete before hashing or decoding, and failed/cancelled temporary snapshots must be cleaned up without touching user files. The original open source must remain available for post-analysis revalidation through publication. Native identity, path replacement, concurrent mutation, seek overflow, short reads, cancellation and cleanup need integration tests. The interface and implementation remain subject to coordinator and library-owner review.

Review of proposed PR #41: a fixed-size `read_at` plus a separate borrowed cursor is sufficient in principle for synchronous libsndfile virtual I/O, but the adapter must translate `SEEK_SET`, `SEEK_CUR` and `SEEK_END` signed offsets with checked arithmetic and explicitly reject sizes/positions not representable in `sf_count_t`. The cursor currently rejects seeking beyond EOF; verify whether libsndfile requires such seeks for supported formats and make failure explicit rather than clamping. A zero-byte callback request must return zero without incorrectly recording EOF or an error. Since a valid source may return short data, the read callback must accumulate short reads until the request is satisfied or a terminal status occurs; retain a sticky cancellation/error distinct from EOF and check it after libsndfile returns, including when a partial read has already been delivered. Catch all C++ exceptions at every C callback boundary and translate them to a sticky error. Specify source lifetime through `sf_close`, worker confinement and cancellation during blocking I/O. The snapshot immutability and original-file verification remain external prerequisites. Test all supported real codecs through virtual I/O, including truncated/corrupt files, short reads, negative/overflowing seeks, zero requests, exceptions and cancellation, alongside native identity/path-replacement scenarios.

For the Linux source-tree experiment (not an installed SDK), use the dependency spike's built Essentia checkout and run:

```sh
cmake -S . -B /tmp/beatglass-tonal-build -DBUILD_TESTING=ON -DBEATGLASS_BUILD_TONAL_SPIKE=ON \
  -DESSENTIA_INCLUDE_DIR=/path/to/essentia/src/essentia \
  -DESSENTIA_LIBRARY=/path/to/essentia/build/src/libessentia.a \
  -DCMAKE_CXX_FLAGS=-I/path/to/essentia/src
cmake --build /tmp/beatglass-tonal-build -j4
ctest --test-dir /tmp/beatglass-tonal-build --output-on-failure
```

Install Eigen3 development files and make the pinned Catch2 source available to CMake or allow its pinned download. A normal installed Essentia puts `version.h` alongside its public headers, so the source-tree `CMAKE_CXX_FLAGS` workaround is unnecessary there. Compiler, ABI, static dependencies and runtime libraries must match; this example is not a packaging recipe. The experimental source emits a window estimate only; no beat timestamps or chord timeline are implemented here.

The experimental Linux CI job runs `docker build -f tests/spikes/tonal-ci/Dockerfile -t beatglass-tonal-ci .`. It builds the pinned Essentia source and runs the real tonal CTest cases along with the dependency-light suite. The image digest, Essentia commit and Eigen package version are fixed; Ubuntu transitive packages and network availability are not fully locked. This hosted check does not establish native product or musical-accuracy qualification.
